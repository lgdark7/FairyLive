
Milestone 15-C Video Pipeline & Audio Discontinuity Investigation & Fix Report
1. Root Cause Analysis: Video Pipeline Stalling (~11.18s Span, 4.38 FPS, 24,224 ms A/V Delta)
During the initial 35-second Creator Studio live broadcast test, video PTS stalled at 11.181 seconds (49 frames, 4.38 FPS) while audio progressed normally to 35.280 seconds, resulting in an A/V desynchronization delta of 24,224 ms.

The 11-Stage Pipeline Trace & Empirical Breakdown:
MediaProjection / VirtualDisplay: On Android 15 (Pixel 8 API 35 AVD), VirtualDisplay produces new graphic buffers only when the screen surface updates (e.g., during active touch, scrolling, or UI invalidation).
SurfaceTexture onFrameAvailable: In the validation harness, user interactions (drag, HUD toggle, tab switching, camera/mic toggles) occurred during the first ~11 seconds. onFrameAvailable fired 49 times during this interaction period, then stopped firing completely once user input ended.
SurfaceTexture.updateTexImage(): In GlesRenderer.consumeNewFrame(force = fromCallback), force is only true when driven by onFrameAvailable. During the 16 ms polling fallback (fromCallback = false), consumeNewFrame returned false because st.timestamp == lastCaptureTimestampNanos.
OverlayCompositor drawFrame() [PRIMARY ROOT CAUSE]:
Because isCaptureNew == false and isCameraNew == false when the screen was idle, the compositor skipped 100% of render iterations for the remaining 24 seconds, terminating all frame composition.
EGL Presentation Timestamp [SECONDARY ROOT CAUSE]:
In GlesRenderer.drawFrame():
captureSurfaceTexture.timestamp was tied to the display producer's timestamp rather than the broadcast session monotonic clock. When the screen did not update, captureTs remained frozen at 11.181s.
MediaCodec Input Submission: EGL14.eglSwapBuffers received zero invocations after second 11.
MediaCodec Output Dequeue: HardwareVideoEncoder.drainLoop() was starved of input frames and dequeued zero output buffers after second 11.
H264 Packet Creation: StreamPipeline.onVideoFrame() was not invoked; video packet generation ceased.
FLV Mux Timestamp: Normalized video timestamps stalled at 11,181 ms.
RTMP Transmission: Zero video RTMP chunks were transmitted over TCP port 19350 after second 11.
RTMP Ingest Parser: Ingest recorded audio chunks continuously up to 35,830 ms, resulting in the 24,224 ms discrepancy.
2. Root Cause Analysis: Audio Discontinuity (56 ms Gap) & Threshold Architecture
A. Root Cause of the 56 ms Discontinuity:
In StreamPipeline.kt, when AacMediaCodecEncoder produced the CSD / Codec-Specific Data config frame (BUFFER_FLAG_CODEC_CONFIG), the pipeline immediately queued an AAC sequence header with an arbitrary session timestamp (550 ms).
The first compressed audio data access unit was dequeued at 606 ms.
The difference between the sequence header tag (ts = 550) and the first audio access unit (ts = 606) was 56 ms. Subsequent AAC access units maintained a steady delta of 23.22 ms.
Furthermore, in AudioCaptureEngine.kt, startTimestampUs was originally initialized before AudioRecord.startRecording() completed its initial blocking read, creating an artificial startup drift offset.
B. Verification of GAP_COMPENSATION_THRESHOLD_US:
In AudioCaptureEngine.kt line 306, the production threshold is strictly 40,000 µs (40 ms):
In Milestone13StressUnitTest.kt, the unit test verifies driftUs > 40_000L.
The prior mention of "50 ms" in documentation was an errant prose reference; the codebase and architectural contract are consistently 40 ms (40_000L µs).
3. Engineering Fixes Implemented
1. Continuous Broadcast Pacing (OverlayCompositor.kt)
Updated renderFrame():
If fromCallback == true (source active): drops callbacks arriving faster than intervalNs * 0.85 to enforce the target framerate ceiling (e.g., 24 or 30 FPS) without over-encoding.
If fromCallback == false (periodic 16 ms poll): checks if elapsedSinceLastNs >= intervalNs. If a full frame interval has elapsed, it does not skip rendering. It composites the current screen texture and active animated overlays (GIF, widgets, goals), keeping broadcast video moving monotonically at the target framerate.
Added guard: if (captureFramesReceived.get() == 0L && cameraFramesReceived.get() == 0L) return, ensuring the compositor does not push empty frames before the stream capture actually begins.
Updated applyScene() to update sceneManager.switchScene synchronously so scene state is immediately consistent across threads.
2. Monotonic EGL Presentation Timestamping (GlesRenderer.kt)
Added presentationTimeNs: Long = 0L to drawFrame().
Anchored presentation timestamps directly to com.fairylive.app.core.common.MediaClock.nanoTimeSource().
Guaranteed strictly monotonic progression: val ptsNs = maxOf(targetPtsNs, lastPresentedTimestampNs + 1_000_000L) so MediaCodec never encounters non-increasing timestamps.
Reset lastPresentedTimestampNs = 0L on initialize() and release().
3. Video Framerate Plumbing (FairyStreamService.kt)
Forwarded target fps from VideoEncoderConfig directly into overlayCompositor.start(encoderSurface, encW, encH, fps).
4. Audio Monotonicity & Sequence Header Synchronization
AudioCaptureEngine.kt: Anchored startTimestampUs on the first genuine audio read (if (totalSamplesRead == 0L) startTimestampUs = wallClockPtsUs), ensuring zero startup false-positive gap triggers. Standardized all audio time calculations on MediaClock.nanoTimeSource().
StreamPipeline.kt: Updated onAudioFrame() so that when frame.isConfigFrame arrives, it caches audioPacketizer.setAudioSpecificConfig(frame.data) and emits the sequence header tagged with the exact ptsMs of the first compressed audio packet.
tools/m15c_rtmp_flv_recorder.py: Updated audio PTS continuity evaluation to evaluate consecutive AAC audio access units (is_seq == False).

Milestone 15-E is technically strong and the architectural hardening work can be accepted, but I would not mark the entire milestone as fully production-approved yet.

The reason is important: the dossier proves the underlying editor architecture much better than it proves the actual user-facing Creator Studio experience.

1. What I am approving ✅
A. Single Source of Truth — PASS
The model/inspector synchronization is exactly the direction FAIRY LIVE needs.

The dossier establishes that inspector changes are committed through:

BroadcastSceneManager.updateOverlayInActiveScene()

and that the canvas, inspector and compositor consume the same scene state.

Decision: 🟢 PASS

This addresses one of the major risks from the earlier editor implementation: UI state drifting away from the actual broadcast scene.

B. Undo / Redo — PASS
The multi-step test is particularly important:

Add A → Add B → Mutate A → Reorder → Delete B → Undo ×5 → Redo ×5

That is substantially better evidence than simply testing one undo operation.

Decision: 🟢 PASS

The bounded history architecture from M15-B combined with the M15-E state-tree verification is acceptable.

C. Nine Overlay Types Serialization — PASS
The dossier explicitly covers:

TEXT
IMAGE
PNG
GIF
FACECAM
GOAL
LOWER_THIRD
ALERT
WIDGET
and includes meaningful properties rather than merely serializing the overlay type.

Decision: 🟢 PASS

This is an important foundation for scenes surviving:

backgrounding
process death
relaunch
undo/redo
export/import
D. Missing Asset Handling — PASS
Graceful degradation for deleted/moved assets is a strong production requirement.

The replacement/fallback mechanism is also a good decision.

Decision: 🟢 PASS

E. Locked Layers — PASS
The requirement that locked elements reject:

dragging
resizing
deletion
while retaining lock state through serialization and undo/redo is appropriate.

Decision: 🟢 PASS

F. Performance / Scene Scaling — PASS, WITH ONE CAVEAT
Testing:

5 → 10 → 15 → 20 overlays

is useful.

However, the dossier gives the conclusion:

"zero memory leaks, smooth layout updates, and bounded CPU overhead"

without providing the actual measured CPU/memory/frame-time numbers.

So I accept the test as evidence for this milestone, but I would not use it as proof of a quantified performance guarantee.

Decision: 🟢 PASS for M15-E / 🟡 quantified performance evidence incomplete

3. Codec Boundary — 🟢 PASS
The dossier correctly states:

Video: c2.android.avc.encoder
Audio: c2.android.aac.encoder

And, importantly, it identifies the AVC encoder on the Pixel 8 AVD as software fallback.

That terminology is correct and should remain that way.

Do not describe this validation as proving physical hardware encoding.

Decision: 🟢 PASS

Reported:

against a:

That's comfortably inside the limit.

Decision: 🟢 PASS

5. The BIG Issue: Creator Studio UI ❌
This is where I would not accept the dossier's "Project Complete" statement yet.

The previous screenshots you provided showed several genuine UX/editor problems:

Preview/editor problems
Preview feels like a basic container rather than a professional composition workspace.
Selection handles/selection state are visually awkward.
Editing is heavily dependent on modal bottom sheets.
There is too much UI competing with the actual canvas.
Layer controls consume significant screen space.
The editor doesn't feel optimized around the preview.
Some dialogs obscure almost the entire composition.
The visual hierarchy is inconsistent.
The current theme feels more like a debug/developer interface than a polished streaming studio.
Overlay editing workflows aren't sufficiently contextual.
Asset workflows are incomplete.
And you specifically identified:

"there is no add gif only showing gif"

That's an important distinction.

Displaying GIF as an option is not the same as implementing a complete GIF workflow.

A production editor should have something like:

Add → GIF → Select GIF → Preview → Configure → Place → Edit

not simply:

Add → GIF

6. Why 216/216 Tests Does NOT Close This Issue
This is the key distinction for the milestone.

Automated tests can establish:

"The underlying system behaves correctly under the tested conditions."

They cannot establish:

"The editor is intuitive, visually polished, comfortable to use, and free of interaction glitches."

Likewise, serialization tests don't prove that:

dragging feels correct,
resizing feels correct,
handles don't jump,
the selected layer is obvious,
bottom sheets don't interfere with editing,
the preview feels responsive,
GIF importing works from the user's perspective,
the UI hierarchy is good.
Therefore:

216/216 PASS ≠ UI production approval
Both kinds of validation are necessary.

8. What I Recommend We Do Next
Do NOT start changing the streaming backend again.

The streaming architecture has already gone through substantial hardening.

The next work should be concentrated on:

Creator Studio UX / Editor 2.0
Priority 1 — Rebuild the preview experience
The preview should become the center of the screen.

Think:

┌──────────────────────────────┐
│  Scene              Undo Redo│
│                              │
│       ┌──────────────┐       │
│       │              │       │
│       │    PREVIEW   │       │
│       │              │       │
│       └──────────────┘       │
│                              │
├──────────────────────────────┤
│ Selected layer               │
│ [Edit] [Move] [Duplicate]    │
├──────────────────────────────┤
│ + Add    Layers    Scenes    │
├──────────────────────────────┤
│ Camera   Mic       GO LIVE   │
└──────────────────────────────┘
The preview should get more space, not less.

Priority 2 — Fix selection/editing
We need a robust editor interaction model:

single tap → select
drag → move
corner handles → resize
pinch → scale
rotation gesture → rotate
long press → contextual actions
locked layer → no manipulation
snapping → subtle guides
selected layer → clear but minimal outline
deselect → tap empty preview
And most importantly:

No accidental movement when opening an editor.

Priority 3 — Stop using huge dialogs for everything
Instead of:

select element → huge bottom sheet covering preview → edit → close

use a compact inspector / contextual editor.

For example:

[ L ] [ C ] [ R ]
Only show controls relevant to the selected element.
