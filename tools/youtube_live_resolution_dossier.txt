## 1. Root Cause Analysis of Previous YouTube Studio "No data" State

When YouTube Studio was initially inspected in Google Chrome (PID 11548), the live dashboard displayed:
- `"No data"`
- `"Connect your encoder to go live"`
- `"Start sending us your video from your streaming software to go live"`

An in-depth physical pipeline audit revealed three distinct root causes:
1. **Missing SPS/PPS Extraction from `MediaCodec` Output Format**:
   On the Exynos hardware encoder (`c2.exynos.h264.encoder`), `prepend-sps-pps-to-idr-frames=0`. The encoder emitted SPS/PPS out-of-band via `csd-0` and `csd-1` inside `MediaCodec.INFO_OUTPUT_FORMAT_CHANGED`. `HardwareVideoEncoder` was not extracting these buffers or forwarding them to `H264FlvPacketizer`. Consequently, `cachedSps` and `cachedPps` remained null, and zero AVC Sequence Headers (`AVCDecoderConfigurationRecord`) were ever emitted to the RTMP connection.
2. **Non-Zero Timestamp on Sequence Headers**:
   When sequence headers were constructed, they used the current presentation timestamp (`ptsMs = 423819`) instead of `0L`. Per Adobe RTMP/FLV specifications and YouTube Live ingest requirements, decoder configuration records (both AVC and AAC sequence headers) MUST have `timestampMs = 0L` to initialize the demuxer. Any non-zero timestamp causes YouTube's ingest to drop the packet.
3. **Missing RTMP Server Control Loop & Publish Status Handling**:
   `RtmpClient` sent `publish` but did not wait for or validate the server's AMF0 `onStatus` (`NetStream.Publish.Start`) response. Furthermore, `RtmpClient` lacked a background reader thread for incoming server messages during streaming. When YouTube sent `User Control Message: Ping Request` (Event 6), the client never responded with `Ping Response` (Event 7), and unread control bytes accumulated in the TCP receive buffer, leading to server-side socket resets after 30 seconds.

## 2. Engineering Fixes Implemented

1. **`HardwareVideoEncoder.kt` & `VideoEncoderConfig.kt`**:
   - Added `format.setInteger(MediaFormat.KEY_PREPEND_HEADER_TO_SYNC_FRAMES, 1)` to request in-band parameter sets on supporting devices.
   - Added `onSpsPpsAvailable: ((ByteArray, ByteArray) -> Unit)?` callback.
   - Extracted `csd-0` (SPS) and `csd-1` (PPS) byte buffers on `MediaCodec.INFO_OUTPUT_FORMAT_CHANGED` and forwarded them immediately.
2. **`AacMediaCodecEncoder.kt` & `AudioPipeline.kt`**:
   - Added `onAudioSpecificConfigAvailable: ((ByteArray) -> Unit)?` callback.
   - Extracted `csd-0` (`AudioSpecificConfig`) from audio encoder `INFO_OUTPUT_FORMAT_CHANGED` and forwarded to the audio packetizer.
3. **`H264FlvPacketizer.kt` & `AacFlvPacketizer.kt`**:
   - Strictly enforced `timestampMs = 0L` in `buildAvcSequenceHeader()` and `buildAacSequenceHeader()`.
   - Guaranteed `stripStartCode()` strips any 3-byte (`00 00 01`) or 4-byte (`00 00 00 01`) Annex B start codes before packing into `AVCDecoderConfigurationRecord`.
4. **`StreamPipeline.kt`**:
   - Wired `setSpsPps()` and `setAudioSpecificConfig()` to immediately enqueue timestamp-0 sequence headers into the priority packet queue ahead of any media frames.
   - Re-injected metadata and timestamp-0 sequence headers upon reconnection.
5. **`RtmpClient.kt`**:
   - Implemented `waitForPublishResult()` to validate server AMF0 `onStatus` (`NetStream.Publish.Start`) and reject bad stream keys (`NetStream.Publish.BadName`).
   - Implemented background `readThread` (`FairyRtmpReader`) that handles server `Set Chunk Size` (Type 1), automatically responds to RTMP `Ping Request` (Type 4 Event 6) with `Ping Response` (Type 4 Event 7), and logs server commands.
   - Thread-synchronized `chunkWriter.writeMessage()` to guarantee safety between outgoing media packets and control ping responses.
6. **`FairyStreamService.kt`**:
   - Wired encoder callbacks directly to `streamPipeline.setSpsPps()` and `streamPipeline.setAudioSpecificConfig()`.
   - Ensured clean teardown and unregistration in `stopStreamService()` and `onDestroy()`.
