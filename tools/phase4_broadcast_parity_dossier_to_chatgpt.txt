2. ROOT CAUSE AUDIT & FORENSIC INVESTIGATION
--------------------------------------------------------------------------------
A) THE "CIRCLE" ARTIFACT:
- Forensic Origin: app/src/main/java/com/fairylive/app/core/compositor/OverlayCompositor.kt:647.
- Cause: FairyStreamService.kt (lines 377-379) was calling overlayCompositor.addSampleMultiOverlayScene().
  This hardcoded test method explicitly injected an "animated_orbit" sample GIF:
    id = "animated_orbit", x = 0.04f, y = 0.78f, width = 0.12f, zIndex = 12
  This created a rotating circular orbital graphic on every broadcast frame.
- Secondary Factor: view_streamer_floating_hud.xml defined circular action buttons (@drawable/bg_hud_circle_button) that hovered over the captured display.
- Resolution: Permanently purged addSampleMultiOverlayScene() from FairyStreamService. Live compositor now directly binds to app.sceneManager.activeScene.

B) CREATOR CONTROLS / HUD IN BROADCAST FRAMES:
- Cause:
  1. FairyStreamService used MediaProjectionConfig.createConfigForDefaultDisplay(), forcing full-screen display capture.
  2. StreamerFloatingHudManager attached view_streamer_floating_hud to activity.window.decorView.
  3. When the creator was in Creator Studio, the device display contained the studio controls, selection handles, crop handles, and floating HUD.
  4. MediaProjection captured that display, and OverlayCompositor layered sample overlays on top, baking creator controls into the stream.
- Resolution:
  1. Implemented CaptureSource.SINGLE_APP using Android 14+ MediaProjectionManager.createScreenCaptureIntent(), routing to Android's OS task-isolation picker (RECORD_CONTENT_TASK). This isolates the selected app/game and automatically excludes FAIRY LIVE, notifications, and floating overlays.
  2. Isolated StreamerFloatingHudManager: MainActivity strictly suppresses the floating HUD whenever CreatorStudioFragment is in the foreground.
  3. Bounded all studio editing handles (crop notches, rotation stem, corner grips) strictly to BroadcastPreviewView.onDraw(canvas). They never enter the GLES broadcast render pipeline.

C) PREVIEW VS BROADCAST GEOMETRY MISMATCH:
- Cause:
  1. BroadcastPreviewView.kt was using elem.normalizedWidth * 0.4f * viewH for auto-height elements, whereas OverlayTransform and GlesRenderer computed (normalizedWidth * streamWidth) / sourceAspect.
  2. FairyStreamService never loaded the active scene from SceneRepository/BroadcastSceneManager at launch, instead rendering the 5 sample overlays.
- Resolution:
  1. Synchronized aspect ratio resolution across BroadcastPreviewView, OverlayTransform, and GlesRenderer.
  2. FairyStreamService.handleStartCapture now executes overlayCompositor.applyScene(activeScene).

4. GEOMETRY & TRANSFORM PARITY SPECIFICATION
--------------------------------------------------------------------------------
- Center-Anchored Coordinates:
    cx = (normalizedX + normalizedWidth / 2f) * width
    cy = (normalizedY * height) + baseH / 2f
    resolvedW = normalizedWidth * width * scale
    resolvedH = baseH * scale
    resolvedL = cx - resolvedW / 2f
    resolvedT = cy - resolvedH / 2f
- Aspect Ratio Mapping:
    aspect = 4.0f (TEXT/LOWER_THIRD), 2.5f (ALERT), 1.0f (DEFAULT/STICKER/GIF)
    baseH = (normalizedWidth * width) / aspect
- Crop Invariants:
    cl < cr - 0.05f,  ct < cb - 0.05f (strictly clamped in preview & GLES texture sampling)
- Rotation Invariance:
    Inverse rotation coordinate unmapping:
      dx = px - cx, dy = py - cy
      unrotatedX = cx + (dx * cos(-rad) - dy * sin(-rad))
      unrotatedY = cy + (dx * sin(-rad) + dy * cos(-rad))
